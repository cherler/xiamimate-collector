## 〇、Keepa + Amazon 自动化采集流水线（新增）

> 已实现代码在 `data_collector/cross_border_data/` 下，详见 `AUTO_COLLECT_README.md`

### 0.1 概述

Temu 抓取因反爬暂停后，当前已切换到 **Keepa API** 采集 Amazon 商品的历史价格、BSR、评论、月销等数据。

- **API 费用**：€29/月，1440 token/天
- **数据粒度**：日级别，历史可回溯 2-4 年
- **存储**：DuckDB 本地分析库 (`data_platform/storage/warehouse/local_analytics.duckdb`)

### 0.2 当前 Keepa 采集流程

```
Phase 1: ASIN 发现 (免费或极低消耗)
  ├── Bestsellers API → 每品类几千~几十万 ASIN (0 token)
  ├── 关键词搜索 → 按结果页计费 (10 token/页)
  └── 种子文件 → 手工 CSV

Phase 2: 历史数据采集 (主要消耗)
  ├── 取待采集 ASIN (未拉取优先 > 过期优先 > 高优先级优先)
  ├── Keepa product API → ~2 token/ASIN
  ├── DuckDB INSERT OR REPLACE → 按 (asin, domain, date) 去重
  └── 标记 last_fetched_at + fetch_count++

Phase 3: Google Trends (免费)
  ├── 从商品标题自动提取搜索词
  └── pytrends 拉取 → DuckDB 入库
```

### 0.3 ASIN 状态管理

| 状态 | 判定条件 | 说明 |
|------|---------|------|
| 未拉取 | `last_fetched_at IS NULL` | 新发现，从未采集过历史 |
| 待更新 | `last_fetched_at < 当前时间 - 14天` | 超过 stale_hours 需要更新 |
| 已更新 | `last_fetched_at ≥ 当前时间 - 14天` | 跳过，不重复采集 |

### 0.4 当前 Keepa DuckDB 数据表

| 表名 | 作用 | 主键 |
|------|------|------|
| `curated.keepa_asin_registry` | ASIN 注册表 + 状态跟踪 | (asin, domain) |
| `curated.keepa_product_history` | 价格/BSR/评论/销量全历史 | (asin, domain, date) |
| `curated.google_trends_daily` | 搜索热度日级数据 | (keyword, geo, date) |
| `curated.collection_log` | 每次采集运行日志 | 自增 ID |

### 0.5 常用 CLI 命令

```bash
# 一键自动采集 (发现→拉取→Trends)
python -m data_collector.cross_border_data auto-collect

# 查看 DuckDB 统计
python -m data_collector.cross_border_data db-stats

# 单独发现 ASIN
python -m data_collector.cross_border_data discover-asins --category 172282
```

## 一、当前只做什么

这版文档不再继续展开泛化的跨境渠道调研，而是只保留当前真正要落地的两条线：

1. `Temu 商品销量和售价数据构建`
2. `Temu 商品对应供应商的发现与映射`

也就是说，当前重点不是再扩渠道，而是把已有的商品侧数据结构和供应商侧方法收敛成可执行流程。

## 二、当前商品销量售价数据怎么落地

### 2.1 当前输入表

当前数据构建器围绕 5 张表：

| 表名 | 作用 | 主要字段 |
|------|------|---------|
| `temu_product_snapshot` | 商品详情页主表 | `price` `original_price` `discount_rate` `sold_display` `review_count` `rating` |
| `temu_sku_snapshot` | SKU 库存与购买限制 | `is_available` `max_order_qty` `stock_hint` |
| `temu_review_daily` | 评论日增特征 | `new_review_count` `photo_review_count` `low_star_review_count` |
| `temu_rank_daily` | 关键词结果页排名 | `keyword` `rank` `price` `review_count` |
| `temu_external_signal` | 外部需求与辅助销量代理 | `google_trends_index` `tiktok_heat_score` `third_party_estimated_daily_sales` |

### 2.2 当前输出表

当前构建器会输出 4 份文件：

1. `temu_base_training_dataset.csv`
2. `temu_pytorch_forecasting_dataset.csv`
3. `temu_xgboost_dataset.csv`
4. `temu_dataset_manifest.json`

### 2.3 当前目标列怎么定义

当前目标列是 `proxy_daily_sales`。

它的优先级是：

1. 前台累计销量差分
2. 第三方估算日销量
3. 评论增长换算销量代理

这意味着它适合做：

- 趋势预测
- 相对销量排序
- 补货节奏判断

它不适合直接作为真实财务销量。

### 2.4 当前最重要的特征

目前最关键的不是把字段堆多，而是把下面这些特征抓稳定：

- `价格特征`：售价 原价 折扣率
- `销量代理特征`：销量标签差分 评论增量 第三方销量估算
- `库存压力特征`：最大可购数变化 可售 SKU 数变化
- `竞争特征`：关键词排名 排名变化 评论密度
- `外部需求特征`：Google Trends 指数 TikTok 热度

## 三、当前推荐的数据构建流程

### 3.1 每日流程

1. 先抓商品详情页，落 `temu_product_snapshot`
2. 再抓 SKU 规格区，落 `temu_sku_snapshot`
3. 再抓评论信息，更新 `temu_review_daily`
4. 再按关键词抓搜索结果页，更新 `temu_rank_daily`

### 3.2 每周流程

1. 更新 `Google Trends` 关键词热度
2. 补录第三方销量估算和跨平台同款数
3. 写入 `temu_external_signal`

### 3.3 数据集构建命令

```bash
python -m data_collector.temu_forecast build-dataset \
  --product-snapshot-file data_collector/examples/temu_product_snapshot_sample.csv \
  --sku-snapshot-file data_collector/examples/temu_sku_snapshot_sample.csv \
  --review-daily-file data_collector/examples/temu_review_daily_sample.csv \
  --rank-daily-file data_collector/examples/temu_rank_daily_sample.csv \
  --external-signal-file data_collector/examples/temu_external_signal_sample.csv \
  --output-dir data_collector/forecast_datasets/temu_demo
```

## 四、商品供应商怎么找

你现在这条线，最实用的目标不是一步找出“唯一正确工厂”，而是先建立 `候选供应商池`，再做人工确认。

### 4.1 推荐的找供应商方法

#### 方法一：主图反查同款

最直接的方式是把 Temu 商品主图拿去 `1688` 或 `Alibaba.com` 做图搜。

适合找：

- 标准品
- 外观高度一致的收纳类 箱包类 家居小件
- 组合款和套装款

重点看：

- 图片是否一致
- SKU 规格是否一致
- 包装方式是否一致
- 供货价和 MOQ 是否落在合理区间

#### 方法二：标题拆词找厂

不要直接整句搜索，要把标题拆成：

- 功能词
- 材质词
- 场景词
- 规格词

例如一个包类商品，通常要拆成：

- `insulated`
- `lunch bag`
- `leakproof`
- `large capacity`

再把这些词换成中文货描去 `1688`、阿里国际站和行业垂类站搜。

#### 方法三：价格带反推供应商

如果 Temu 前台售价很低，可以先做一轮反推：

$$
可接受供货价 \approx 前台售价 - 平台扣点 - 物流成本 - 活动成本 - 预留利润
$$

然后拿这个区间去筛供应商。

这一步的作用不是算得绝对精确，而是先把明显不可能的候选排掉。

#### 方法四：跨平台同款回查

对一个 Temu 商品，可以同时去这些地方看：

- `Amazon` 看是否有成熟款型
- `1688` 看是否有现成工厂货盘
- `Alibaba.com` 看是否有外贸标准货描
- `TikTok Shop` 看是否有人在卖同款短视频爆品

如果多个平台都能找到同款，供应商匹配会更稳定。

#### 方法五：品牌和店铺线索反查

如果 Temu 页面或包装细节里能拿到这些线索，就不要浪费：

- 店铺名
- 品牌词
- 货号
- 包装文案
- 发货地或仓地

这些线索可以拿去 `ImportYeti`、企业主体工具、搜索引擎继续反查上游。

#### 方法六：用平台型供应链工具做候选池增强

你提到的 `阿里悟空` 和 `遨虾`，我建议你重点验证这几件事：

1. 能不能做 `同款图搜`
2. 能不能拿到 `工厂画像`
3. 能不能拿到 `报价 MOQ 样品 交期`
4. 能不能导出或至少稳定复制结果

如果它们能覆盖以上两到三项，就很值得放进主流程里，优先级会很高。

当前我不建议先假设它们一定可用，先把它们定义成 `待验证渠道` 更稳。

### 4.2 我更推荐的供应商数据结构

下一阶段建议先建两张表：

| 表名 | 作用 | 说明 |
|------|------|------|
| `supplier_candidate_pool` | 候选供应商池 | 先把所有可能供应商收入池，不急着强确认 |
| `product_supplier_link` | 商品与供应商映射 | 只记录已经人工确认过的匹配 |

候选池建议至少保留：

- 供应商平台
- 供应商名称
- 链接
- 图搜匹配分
- 报价
- MOQ
- 是否支持拿样
- 交期
- 可信度评分

映射表建议至少保留：

- 匹配类型
- 匹配依据
- 当前报价
- 联系状态
- 最后核验时间

### 4.3 落表规则

当前供应商构建脚本采用下面这套规则：

1. `supplier_candidate_pool` 先收所有候选，不在这一步删除低分候选
2. `candidate_id` 由 `product_id + supplier_platform + supplier_name` 自动生成
3. 同一个 `candidate_id` 多次出现时，保留最新抓取时间，同时对匹配分和 MOQ 做去重聚合
4. `source_confidence` 优先取原始值，缺失时按图搜分 标题分 规格分自动补齐
5. `product_supplier_link` 只保留人工确认通过的供应商，不自动从候选池直接升级

### 4.4 脚本入口

当前可以直接用下面的命令把供应商表落出来：

```bash
python -m data_collector.temu_forecast build-supplier-tables \
  --product-snapshot-file data_collector/examples/temu_product_snapshot_sample.csv \
  --supplier-lead-file data_collector/examples/temu_supplier_leads_sample.csv \
  --supplier-review-file data_collector/examples/temu_supplier_review_sample.csv \
  --output-dir data_collector/forecast_datasets/temu_supplier_demo
```

### 4.5 实操上最稳的一条路径

如果你要尽快落地，我建议按这个顺序做：

1. `Temu 商品池` 先稳定抓 2 到 4 周
2. 对销量高且价格带合理的商品做 `1688 图搜`
3. 找到 3 到 10 个候选供应商后建 `supplier_candidate_pool`
4. 对高匹配候选做人工核验，沉淀 `product_supplier_link`
5. 再看是否要把供应商价格 MOQ 样品状态并到训练特征里
